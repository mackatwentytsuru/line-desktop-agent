# 学んだこと(段 1: 読むだけ)

## 効いたこと
- `uiautomation` パッケージ(venv の中だけ)で、キー・クリック・前面切り替えなしに、トーク一覧と ChatWindow の本文が読めた。
- 窓の特定は「プロセス名 LINE(QueryFullProcessImageNameW)+ UIA の ClassName(AllInOneWindow / ChatWindow)」。最上位から深さ 2 まで探す。
- 木は一度「Node」の写しにしてからパースする。パーサーは UIA なしで試験できる(にせもの木)。
- 実測: 1 回の実行は約 7 秒(木の全走査が主)。前後で前面の窓は変わらなかった。「一括送信」の窓は他の窓の後ろ(最小化ではない)でも読めた。
- 安全の試験 `tests/test_no_actions.py` は src/ の全文を禁止語で検索する。コメントにも禁止語を書かないこと(大文字小文字も区別しない)。

## つまずきと直し
- トーク一覧の「時刻」は午前/午後 H:MM だけでなく「2026年11月9日」「11月10日」などの日付もある。末尾が「…」で切れた一言には時刻が付かない(138 件中 9 件)。時刻の正規表現に日付形を足した。
- 「名前, 一言, 20…」のように時刻が切れる行がある → 時刻を取れなくても壊れないようにし、raw を必ず残す。
- 名前や本文に「, 」が入ると分解がずれる。未読は 2 番目が整数のときだけ採用。名前に「, 」があるトークは name が不正確になり得る(raw を見る)。
- bash の heredoc で大きなファイルを書くと引用符で壊れた。Write ツールで書く。

## 分かったこと
- 一括送信の本文の Text 要素には送信者名が出ない(本人だけのトークのため。グループは未確認)。
- 写真・動画・ファイルは種類だけ(中身は出ない)。動画は長さ、ファイルは名前と期限が名前文字列に入る。
- 読めるのは画面に読み込まれた分だけ(古い分は未確認)。

## 未確認
- 最小化中の窓、グループでの送信者名、古い履歴のスクロール。

# 段 2: 見張り + 保存 + 探す

## 効いたこと
- **速さ**: 一覧の読みは約 7 秒 → 約 0.4〜0.7 秒(CLI 全体)。遅かった本当の原因は木の走査ではなく、窓探しの `GetRootControl().GetChildren()`(約 5〜6 秒)。Win32 の窓の一覧(EnumWindows)でプロセス名 LINE の窓だけ拾い、UIA の `ControlFromHandle` で包むと約 0.1 秒。
  - さらに本体の木は、タイトルバー・影・広告の枠・一覧の行の中身を降りずに読む(`snapshot_main`)。木の走査は約 0.3 秒。
- 保存は標準の sqlite3 だけ。重複の鍵 = (トーク, 日付, 時刻, raw, 同じ組の中の通し番号)。同じ画面を読み直しても新規 0 件(一括送信 73 件、2 回目は new=0)。本当に同じ文が繰り返されても別の鍵になる。古い行は消さない。
- 見張りは 30 秒ごと。STOP ファイルを置くと数秒で終了(1 秒刻みで待つ)。前面の窓のハンドルは毎回ログに書き、3 ティックとも変わらなかった。
- 最初の 1 回(DB が空)は基準を作るだけで知らせは出さない。

## つまずきと直し
- **同じ名前のトークが一覧に複数ある**(138 件中 3 組)。名前を鍵にすると毎回上書きされ、毎ティック「変化」と誤検出された。→ 名前 / 名前#2 のように鍵を分ける。同名のトークは窓との照合ができないので本文は読まない(知らせだけ)。
- 安全の試験は「Select」を大文字小文字なしで探すので、SQL の SELECT も引っかかった。試験は弱めず、store.py では語を 2 つに分けて書いた。
- heredoc に日本語・引用符を長く入れるとシェルが壊れる(段 1 と同じ)。Write ツールで書く。
- 日付は「2026年10月9日」形式。検索の --since のため、保存時に ISO(date_iso)も持つ。

## 未確認
- ChatWindow が開いている状態で新着が来たときの本文取り込み(にせもの木の試験のみ。実機は変化が起きなかった)。
- 窓の先頭が日付の区切りより後から始まる場合、日付が空のメッセージの鍵は前回と食い違い、重複して入ることがある。

## 段 3: スマホへの知らせ(11-10 実測)
- 仕組み: 見張りが events.jsonl に 1 行足す → 開いたままの Claude のセッションが Monitor(tail -F)で受け取る → 中身を見て PushNotification。
- 届いた: Claude アプリを閉じているとき。**アプリでこの会話を開いている最中は、通知は出ない**(画面に出ているので要らない扱い)。PC の画面を使っている最中も出ない。
- Monitor は 30 分で切れるので、張り直しが要る。セッションを閉じると通知は止まる(見張り本体は動き続ける)。
- 自分の発言・オープンチャット・公式アカウントは通知しない(司令塔の判断。段 3 後に、決まりとしてコードに入れる)。

## 送った人の見分け(友だちAのトークで実測)
- 相手: 先頭に「<トーク名>, 」。ただし続けて送った 2 通目以降は名前なしのことがある。
- 自分: 末尾に「, 既読」。相手が読む前は既読が無く、相手の 2 通目と同じ形になる → 文字だけでは決まらない。部品の位置も行の幅いっぱいで、左右の差なし。
- 中身が空の「<名前>, , 午後 3:42」= スタンプか画像の可能性。
- 直すこと: 「, 既読」が付いた行の時刻が取れていない/既読が付いただけで別の発言として保存し直す/グループの一言の頭に「1人, 」が混ざる/オープンチャットの一言の形が「4,262, 305, …」。

# 段 4: 送った人の見分けと知らせの決まり(11-10)

## 効いたこと
- 一言の見分けは順番に決める: 末尾の「, 既読(, 既読 N)」→ 自分(名前の頭より先に見る。自分の発言が相手の名前で始まっても自分) → 先頭の「<トーク名>, 」→ 相手 → 一覧の見出しボタン「<名前>, 1人」なら全部自分 → 直前が相手で同じ分なら相手 → 画面の色。
- 色の見分け(友だちAの窓): 背景は白、自分の吹き出しは緑で右、相手は白で左。「白ではない画素(字・縁・緑)」の横位置の平均と右端で決める。自分は平均 0.84〜0.85・右端 0.97、相手は平均 0.17〜0.24・右端 0.3〜0.68。平均 0.6 以上かつ右端 0.85 以上 → 自分、平均 0.4 以下かつ右端 0.8 以下 → 相手、間は unknown。スタンプ(緑が混ざる絵)でも平均が左なので相手と読めた。
- 色が決まったら、文字からの「同じ分なら相手」の推測より優先する(同じ分の自分の発言を相手と誤るのを避けるため)。
- 画面の写し取りは Pillow の ImageGrab(読むだけ)。窓が他の窓に隠れていると別の色を拾うので、行の左右の端で WindowFromPoint を読み、最前面の窓が LINE の窓でなければ unknown にする。行の見える高さが 30px 未満でも unknown。
- 重複: 鍵を「トーク・日付・時刻・種類・正規化した本文・通し番号」にして、既読が付いただけの行は新規にならず、既存の行の sender を self、read_mark を 1 に更新する。
- 一度きりの移行(`PRAGMA user_version` 2): `line.db.bak_before_v2` に写してから、全行を raw から読み直して、既読で重複した行を併合(112 → 111 行)。
- 一覧の読み: グループは「名前, N人, [未読,] 一言, 時刻」(名前なしグループは名前が「, 」でつながる)、オープンチャットは「名前, 人数, [未読,] 一言, 時刻, 名前」(末尾に名前の繰り返し)。members と kind(friend / group / openchat / official)に分けて、一言がきれいになった。
- 知らせの決まり: 各イベントに notify と reason。オープンチャット・公式・自分だけ・未読が増えていない一覧だけの変化は false。相手か不明の新しい一言、または友だち/グループの未読が増えたら true。`grep '"notify": true' events.jsonl`。
- 新しく開いた窓の中身は、その回に黙って保存する(基準)。見張りを再起動した直後の窓も同じ。

## つまずきと直し
- 一覧の形が変わると(グループの一言から「1人, 」が消える)全グループが一斉に変化と見なされるので、旧版で保存した行(ctype が空)はその回だけ黙って更新する。
- 合成画像の試験では、字の画素が少ないと unknown になる(最低 40 サンプル)。
- 一括送信の窓が他の窓に隠れていると、色の見分けは unknown(隠れ判定が効いた)。

## 未確認・できないこと
- 公式アカウントは一覧の形で見分けられない。名前表(既定: LINE など数個)+ データフォルダの official_names.txt(1 行 1 名)で補う。
- グループ内の発言者名(「山田, 本文, …」)はトーク名と違うので名前では見分けられず、色頼み。
- 暗い配色、背景が白でない配色では色の決まりを測り直す必要がある。
- 色の見分けの実測は、友だちAの画面に見えている 4 行(4/4 正解)と、事前の統計(9/9)だけ。

# 段 5: グループの発言者・システム行・ラベルの変化(11-10)

## 効いたこと
- グループかどうかは、窓の見出しボタン「<トーク名>, N人」(N が 2 以上)で決める(見張りは一覧の kind も渡す)。グループの一言は、先頭の「, 」の前を発言者名として外す。名前のない行(自分の読まれる前の発言・同じ人の続き)は「, 」で分けて 1 つしか欄がないので、名前とは見なさない。
- 発言者名の学習(1 回の読みの中): 返信行・システム行に出る名前と、2 行以上の頭に出る名前を「メンバー」とする。1 回しか出ない名前でも発言者として扱うが、色の見分けが「自分」なら、頭の欄は本文の一部だったと見て名前なしで読み直す(本文に「, 」を含む自分の発言の救済)。
- 返信行「<A>のメッセージへの<B>のリプライ。…」は、B が発言者(B が自分の表示名なら自分)。自分の名前は設定 self_names(config.json)。末尾に 既読 があれば自分。
- システム行(kind=system, sender=system): 「…がグループを退会しました。」「…が…をグループに追加しました。」「グループ通話が開始されました, 参加」「グループ通話が終了しました。」「, ノートを見る」。知らせは出さない。保存はする。
- 重複の鍵から、変わりやすいラベル(期限切れ・既読 N・既読)を取る。ラベルが付いた/既読の数が変わった行は新規にならず、既存の行の raw・text・labels を更新する。
- 知らせの追加の決まり: 見張りを起動した日より前の日付、またはそのトークで保存済みの最新(日付+時刻)より前の新規行は stale=true にして、知らせない。日付が取れない行は判定しない。
- 一度きりの移行(user_version 3): `line.db.bak_before_v3` に写してから、保存済みの raw をグループ規則で読み直し、ラベル違いだけの行を併合(同じ raw の本当の繰り返しは残す)。
- 実測(グループA の窓 75 行): 相手 59 / 自分 11 / システム 5 / unknown 0。見つかった発言者名は 6 つ。

## つまずきと直し
- 鍵の区切りは制御文字 \x1f。移行で新しく鍵を組むときも同じ区切りを使わないと、読み直しで全部が新規になる(試験で発覚)。
- 安全の試験が「Select」を探すので、store.py の SQL は _Q 経由で書く(新しい SQL も同じ)。

## 未確認
- 窓が隠れていて色が取れないとき、1 回しか名前が出ず本文に「, 」を含む自分の発言は「相手」と誤る。
- 先頭の日付が見えない(日付が空の)行は stale 判定ができない。
- 返信の相手 A の名前に「のメッセージへの」が入ると分解がずれる。

# 段 6: 開く・送る(11-10、一括送信だけで実測)

## 効いたこと
- **開く**: 本体の一覧の行(Button)に UIA の Invoke をかけると、最小化していた「一括送信」の窓がすぐ戻って前面に出た(0.0 秒)。キーもクリックも要らない。前面は守りが元の窓へ戻した(前後とも同じ窓)。
- マウスの道(予備): 行の真ん中を 1 回押しても開かず、**2 回押し(ダブルクリック)で開いた**。押す前に点の上の窓が本体の窓か(WindowFromPoint → GA_ROOT)と前面を毎回確かめた。
- **最小化した ChatWindow は UIA の名前が「LINE」になる**(Win32 の題名は「一括送信」のまま)。窓の照合は Win32 の題名(GetWindowTextW)で行う。
- 入力欄は Edit[AutoSuggestTextArea](MessageInputPanel の中)。Value と Text に対応。**送信ボタンは UIA に出ない**(文字が入っていても)。送るには Enter が 1 回要る。
- **Value で入れただけでは LINE は「入力あり」と見なさない**: 画面には文字が出て読み戻しも一致するが、Enter を押しても送られず、文字も改行も変わらなかった(1 回目は failed、入れた文字だけ空に戻した)。
- **先に入力欄をマウスで 1 回押してから Value で入れ、0.3 秒おいて Enter** → 送れた。最後の行に自分の発言として出た(sender=self)。
- 自分の SendInput の入力時刻は少し遅れて記録される。押した直後に基準を取ると、次の確かめで「本人が触った」と誤って止まった。→ 押す前の時刻を覚えて、記録がそこまで進むのを待ってから(最大 0.5 秒)基準を取る。
- SetForegroundWindow は少し遅れて効く。すぐ確かめると失敗に見えるので、0.5 秒まで待つ。予備の UIA の SetFocus は、UIA を持たない窓(Chrome など)で COM の例外を出すので受け止める。
- ctypes: `ctypes.windll.user32` の argtypes を書き換えると、同じ関数を使う uiautomation が壊れた(GetAncestor が型エラー)。自分用に `ctypes.WinDLL("user32")` を別に作る。
- 本人が PC を使っている最中は、3 秒の静かな間が 30 秒以上来ないことが多かった。送信は `--wait-idle 240` で待った。待つのは合言葉を使う前(待ちで止まっても合言葉は減らない)。

## 守りの作り(試験で確かめる)
- 操作は inputguard.py の `run_guarded` が渡す `hands` だけで行う。生の Windows の呼び出しは Win32System の `_act_*` だけ、それを呼ぶのは `_Hands` だけ、`_Hands` を作るのは `run_guarded` だけ。キーは Enter だけ。tests/test_no_actions.py が構文で確かめる。reader・parse・store・watcher などの禁止語の試験は前のまま。
- 元に戻すのは、こちらが変えたものだけ(前面は LINE が前にあるときだけ戻す。カーソルは動かしたときだけ戻す)。

## 未確認
- 一覧にあって窓が開いていないトークを、Invoke で新しい窓として開けるか(一括送信・友だちAはどちらも窓が開いたままで、閉じない決まりのため試していない)。
- 検索欄(LcTextField)に Value で名前を入れて一覧が絞られるか(にせものの試験だけ)。
- LINE の設定で Enter が「改行」になっている PC では送れない(その場合は failed になり、入れた文字を空に戻す作り。実機では未確認)。

## 11-10 17:05 司令塔の実測: 閉じたトークを開く
- 友だちAの窓を閉じた状態から `open 友だちA` → 一覧の行への Invoke だけで開いた(マウス・キーなし)。前面の窓(67552)とカーソル位置は前後で同じ。
- 本人の設定: Enter = 送信、Shift+Enter = 改行(11-10 本人)。送るときの Enter 1 回は、この設定が前提。設定が変わると送れない(改行になる)ので、送ったあとに最後の行を読んで確かめる仕組みは外さない。
- 本人がいったん閉じた窓が、いつの間にか別の番号で開き直っていることがあった(新着で LINE が開いた可能性)。「閉じている」と思い込まず、毎回窓の一覧を読む。

# 段 7: マウスなし・前面なし(11-10、20 ms ごとに前面を見張って実測)

## 効いたこと
- **文字を入れる**: 入力欄の LegacyIAccessible の値の設定は、前面を一度も奪わなかった。UIA の ValuePattern の設定と UIA のフォーカスは、どちらも LINE を前に出した(本人が Claude に打っている最中に前に出た)。
- **Enter**: トークの窓の hwnd へ WM_KEYDOWN / WM_KEYUP(VK_RETURN、lParam はスキャンコード 0x1C、離すときは 30・31 ビット)を PostMessage → 送れた。LINE が裏にあるまま(前面は Claude)で届いた。WM_CHAR は要らなかった。
  - 段 6 で「Value だけでは送れなかった」のは、LINE の窓の中のフォーカスが入力欄になかったためとみられる。一度入力欄がフォーカスを持った窓では、そのまま送れる(フォーカスが別の所にあると送られず、failed になって文字を空に戻す作り)。
- **スクロール**: LcListView に ScrollPattern は無い。トークの窓へ WM_MOUSEWHEEL(lParam は画面の座標)を投函すると、裏のままスクロールした(3 ノッチで約 405px)。その点を別の窓が覆っていても効いた。
- **古い履歴**: 上へ 10 ノッチずつ送り、先頭の行が 3 回続けて変わらなければ「先頭」とみなす。グループA は 30 回で 120 行 → 177 行(2026-09-08 まで)になり、53 件を新しく保存した。いちばん下へは 27 回で戻った。
- **開く**: 最小化中の窓は ShowWindow(SW_SHOWNOACTIVATE)で、前に出さずに戻った。最小化の試験は SW_SHOWMINNOACTIVE を使う(SW_MINIMIZE は別の窓を前に出しうる)。
- **窓の写し取り**: PrintWindow(PW_RENDERFULLCONTENT)なら、隠れている窓の中身も前に出さずに写せた(写真の行の下の「保存 | 名前を付けて保存 | 転送 | Keepメモに転送」が読めた)。
- ClearType の色のにじみがあるので、灰色の文字の帯は「中間の灰色の画素が 15% 以上」で見分ける(実測 23%)。

## できなかったこと(2 回失敗して止めた)
- **添付の保存**: リンクは UIA に出ない(行は葉の Text だけ)。
  - PrintWindow で位置を見つけて WM_MOUSEMOVE → WM_LBUTTONDOWN → WM_LBUTTONUP を投函しても、何も起きなかった。
  - WM_CONTEXTMENU を写真の上へ投函しても、メニューは出なかった。
  - 前面もカーソルも変わらず、ファイルも増えなかった。Qt 6 はボタンの状態を本物のマウスから読む(GetAsyncKeyState)とみられ、投函のクリックは押されていない扱いになる。

## 未確認
- 窓が開いていないトークを一覧の行で開くとき、LINE が新しい窓を前に出すか(守りは、出たら本人の窓へ戻して記録する。試すには窓を閉じる必要がある)。
- 最小化中のトークへの送信(試験の通数の上限のため未実施)。
- 「↓ 最新へ」の帯の UIA の部品(--to-bottom はホイールで代わりにしている)。

# MCP サーバー(11-10)

## 11-10 夜: 添付の保存を「カーソルも前面も変えずに」行う道は無い(原因が分かった)
- 右ボタンの知らせを窓あてに送ると、メニューは前面を変えずに出る。ただし**メニューは送った座標ではなく、本物のカーソルの位置に開く**。
- メニューの項目「名前を付けて保存」に、移動・押す・離すの知らせを送っても動かない(メニューの窓あて/チャットの窓あて/下矢印の 3 通りとも)。
- 見立て: LINE(Qt 6)はマウスの位置とボタンの状態を、知らせの中身ではなく本物のカーソルとボタンから読んでいる。ホイールだけは知らせの中の座標を使うので効く。
- だから、知らせだけのクリックは「本物のカーソルの下」に当たる。狙いを定められず、削除・通報を押すおそれがあるので、この道は使わない。
- 残る道: (1) 本物のクリックを一瞬だけ使う(カーソルを動かして押して戻す)。(2) LINE を別の PC に置き、そこで本物のクリックを使う。

# Chrome 版(LINE 拡張を CDP で動かす、11-10)

## 効いたこと
- ページは React 製。トーク一覧は `[class*="chatlistItem-module__chatlist_item"]`(仮想一覧。約 8 行しか DOM に無いので、スクロール枠の scrollTop を動かして全部集める)、開くのは行の中の `button[aria-label="Go chatroom"]` に `.click()`。メッセージは `.message_list`(`column-reverse` なので DOM は**新しい順**)。
- 1 通ごとに `data-timestamp`(ミリ秒)・`data-direction="reverse"`(= 自分)・`data-message-content-prefix`(「04:31 Aさん 」)・中身の型(text / image / video / file / sticker / reply のクラス)が付く。日付・時刻・送った人・種類が正確に取れる(デスクトップ版の色の推測は要らない)。ファイルは名前・大きさ・`data-expired` も出る。
- **保存**: 各メッセージの `message-module__action_group` に「保存 | 名前を付けて保存 | 転送」が**いつも DOM にある**(ホバーで出る見た目だけ)。文字が `保存` のボタンに `.click()`(信頼されないイベント)だけでダウンロードが始まった。マウスの座標入力は要らなかった。
- ダウンロード: 別の接続で `Browser.setDownloadBehavior`(`allowAndName`, `eventsEnabled: true`)を送り、`Browser.downloadWillBegin` → `downloadProgress(completed)` を待つ。`allowAndName` はファイルを GUID の名前で置く。`suggestedFilename` は blob の uuid で名前が分からない → DOM の名前(ファイル)か、トーク名+日時+拡張子(写真・動画。先頭バイトで判定)で付け替える。付け替えは上書きしない。
- 実測(グループA): wav(約 79 MB)の SHA256 が手元のファイルと一致/pdf(約 14 MB)/写真 3 枚(JPEG)/動画(約 70 MB、約 275 秒、H.264 1280×720)。動画は期限切れではなかった。期限切れの pdf は断る。
- 送信: `textarea-ex`(Shadow DOM のカスタム要素。`rawValue` で中身が読める、`data-is-empty`)に `focus()` → `Input.insertText` → `Input.dispatchKeyEvent`(Enter の keyDown に `text:"\r"`)で送れた。消すときは Backspace の keyDown/keyUp。
- 一覧の種類は `data-mid` の頭文字で分かる(`C`/`R` = グループ、`U` = 友だち)。名前の横の `(10)` が人数。名前はデスクトップ版と同じ文字なので、同じ行を共有できた(グループA の 45 行のうち 33 行が既存行と一致して新規にならない。返信の行は文面の形が違うので重複して入る)。
- 絵文字は `img[alt="(emoji)"]`。デスクトップ版の `￼`(U+FFFC)に置き換えると、同じ文が一致する。

## 裏・最小化・前面(20 ms で測定)
- 最小化すると `document.visibilityState` が hidden、`requestAnimationFrame` は 500 ms で 0 回。タイマーは 100 ms が 138 ms 程度。**`Emulation.setFocusEmulationEnabled(true)` を送ると visible / focus になり、フレームも回る。** 接続を閉じると元に戻る。
- この設定のまま、最小化中に一覧・開く・読み・履歴(56 → 59 通)・保存(wav・pdf・写真・動画)・送信 2 通が動いた。前面の窓もカーソルも変わらなかった(測定は全プロセスの GetForegroundWindow。ログは scratch の probe)。
- 履歴の古い方への読み込みは `.message_list` の `scrollTop = -scrollHeight`(column-reverse は負の方向が上)。子が増えなくなって 3 回で止める。Chrome 版が持つ履歴は短く、グループA で 10/28、友だちAで 10/30 まで。

- `Runtime.evaluate` で `const` を書くと、次の呼び出しで「宣言済み」の構文エラーになる(グローバルに残る)。毎回 `(async () => { ... })()` の中に入れる。
