## 2. 技術別の知見

### a. 自分と相手の発言を見分ける

- ✓ **吹き出しの左右**。wxauto の `elements.py` → `WeChatBase._split`(28〜62 行)。メッセージ行の高さで「システム / 時刻 / 撤回」を判定し、アバターのボタンの `BoundingRectangle.left` が行の中心より左なら相手、右なら `Self`。
  - LINE の行は Text 要素なので、同じ手を使うなら Text の矩形の左端が List 矩形の中心より右か、で判定する(△ 試す価値あり)。
- ✓ **色**。jev-chat-windows の `app/chatapps.py`(`_wechat_me`: 緑、`_kakao_me`: #FEE500)、MsLester は PrintWindow で窓だけ撮って緑/灰を判定し、確信度 0.72 未満や色が混在なら `direction_unknown` にして行動しない。
  - LINE は自分の吹き出しが緑(△ 実機の色で測る)。
- ✓ **右クリックメニュー**。pywechat の `WeChatTools.is_my_bubble`(386 行)。自分の発言だけメニューに「撤回」が出る。副作用があるので我々は採らない。
- △ **LINE 固有の手がかり**(我々の観測から)。
  - 既読 N は自分の送信にだけ付くはず → 自分のメッセージの強い証拠になる。
  - 名前の前置きがない行 = 自分、の可能性。
  - この 2 つ + 矩形の左右 の 3 点が一致したときだけ確定、食い違いは `unknown` にする(MsLester の流儀)。
- ✓ 台帳: MsLester は UIA の `RuntimeId` で本文が同じ 2 通を区別し、状態(discovered / stable / sending / sent / send_unknown / direction_unknown など)をファイルに落とす(`scripts/auto_reply.py`、`work/state.json`)。

### b. 画面を奪わず、キーを打たずにトークを開く

- ✓ 先行事例は全部、検索欄へキー入力か、一覧の項目を `Click`/`DoubleClick`。
  - wxauto `wxauto.py` の `ChatWith`(303 行): セッション一覧の `ListItemControl(RegexName=who).Click(simulateMove=False)`、無ければ Ctrl+F → 検索ボックスに SendKeys。
  - bensonmax の `windows-line-automation.js` `selectChat`(約 360 行): Ctrl+Shift+F → クリップボードへトーク名 → Ctrl+V → Enter → 画面座標クリック。LINE の検索ショートカットが Ctrl+Shift+F であることは ✓。
- ✓ **別窓方式**。wxauto は一覧のトークをダブルクリックして独立した `ChatWnd` にし(`AddListenChat`)、以後はその窓だけを読む。我々の `ChatWindow` クラスと同じ考え方。主窓を触らずに複数トークを監視できる。
- ✓ Qt で InvokePattern / ValuePattern だけで開けた例は、今回の調査では見つからなかった。事例はすべてクリック(座標または `click_input`)かキー入力。
  - △ Qt のボタンは Invoke、QLineEdit は ValuePattern.SetValue に対応しているはず。LcListView の項目の Invoke / SelectionItemPattern.Select は実機で試す価値がある。
- ✓ 窓の特定の守りは d に書く。

### c. 古い履歴を読み込む(遡り)

- ✓ wxauto の `LoadMoreMessage`(506 行): 先頭要素の `BoundingRectangle.top` を覚え、リストへ `WheelUp(wheelTimes=10)` を繰り返し、先頭の位置が変わらなくなったら終端。ホイールはマウス座標を使う(フォーカス不要だが、カーソルは動く)。
- ✓ pywechat の `WeChatTools.py` 1380 行付近も `mouse.scroll(wheel_dist=-100)`。kaosensei は PageUp を連打して全選択コピー。
- ✓ ScrollPattern を使った例は 0 件。△ Qt の UIA は ScrollPattern を出さない可能性が高い(未確認)。
- ✓ dtwang/bensonmax の `copyAllChatToClipboard`(Ctrl+A → Ctrl+C)は、仮想化された一覧では見えている分しか取れないことに注意。bensonmax の README は古い履歴が欠けると書く(line-ext-reader も同じ警告)。
- 方針案: 遡りは「LcListView にホイールを送る」+「先頭が動かなくなったら終端」+ RuntimeId の重複排除。自分で保存した分(段 2 の保存)を正本にする。

### d. 安全に送る・守りの作り方

- ✓ **宛先の窓を一意に特定**(bensonmax `windows-line-automation.js` の `AcquireExactLineTarget`、約 60〜105 行)。
  - プロセス名 LINE.exe・可視・タイトル完全一致・クラスが `^Qt\d+QWindowIcon$`・PID 一致の窓が **ちょうど 1 つ**でなければ中止。
  - `IsWindowEnabled` でモーダルダイアログ中は中止、前面に出して `WinWaitActive` 後に **前面窓の PID を再確認**(`AssertExactLineFocus`)、窓の大きさが小さすぎれば中止。
  - 各キー送信の直前にも前面確認(`GuardedLineSend`)。
- ✓ **クリップボードの守り**(同 `copyAllChatToClipboard`、約 396〜490 行): 退避 → `GetClipboardSequenceNumber` と `GetClipboardOwner` のプロセス ID が LINE であることを確認 → 復元。他アプリのコピーを巻き込まない。
- ✓ **貼ってから確かめる**(wxauto `SendMsg` 425〜429 行): `SetClipboardText` → Ctrl+V → `editbox.GetValuePattern().Value` が空でないことを確認してから Enter。
- ✓ **事後確認と再送禁止**(MsLester): 送る前に `sending` を保存。再起動時に `sending` が残っていれば `send_unknown` にして自動再送しない。送信後は UIA を読み直し、本文ハッシュで新しい行を見つけ、方向(右の吹き出し)も確認して初めて `sent`。`STOP` ファイルで即停止、宛先のタイトルが設定と完全一致しないと動かない。
- ✓ vegeta fork の `send_line_batch`: 各通で宛先を再照合し、結果が不確かなら止めて再送しない。
- ✓ jev-chat-windows(`app/fill.py`): 候補を入力欄に **貼るだけで送信は人**。「送信は永遠に手動」を最終形にするのも選択肢。
- ✓ ありがちな失敗: 64bit の ctypes でハンドルを `c_void_p` に宣言しないと切り捨てられる(fill.py の冒頭コメント)。
- 我々の確認つき返信への採用案: 「下書きを貼る → UIA で入力欄の値と宛先タイトルを読み戻す → 人が承認 → 送信ボタンを Invoke(△ 可否は実機で確認)」。

### e. 新着の検知

- ✓ **一覧の未読バッジ読み**: wxauto `GetSessionAmont`(159 行)は項目の `Name` を正規表現 `\d+条新消息` で見て件数を取る。我々は LINE の一覧項目の Name から同様に取れるはず(△ 形式は実機で確認)。
- ✓ **RuntimeId 台帳**: wxauto `GetNextNewMessage`(184 行)は既知 ID との差分で新着だけ取る。我々の「見張り・保存」と同じ。
- ✓ **Windows の通知を読む**:
  - `UserNotificationListener`(winsdk / pywinrt)。yasb の `windows_notification.py`(100〜110 行、269〜283 行)が **パッケージ無しの Python から**
    `UserNotificationListener.current` → `request_access_async()` → `get_notifications_async(NotificationKinds.TOAST)` を動かしている。許可されなければ空。
  - イベント側は WNF(`RtlSubscribeWnfStateChangeNotification`、`WNF_SHEL_NOTIFICATION_TOTAL`)の件数変化で再読込(0.1 秒まとめ)。undocumented なので壊れうる ✓。
  - 件数でなく本文は `get_notifications_async` から取る(`visual.bindings` の text)。
- ✓ **通知 DB**: `%LOCALAPPDATA%\Microsoft\Windows\Notifications\wpndatabase.db`(+ `-wal`)。`Notification` と `NotificationHandler` を結合、ペイロードは平文 XML(toastcrumbs の README)。履歴の読みに使えるが、消えた行の復元は我々の用途には過剰。
- ✓ jev-chat-windows の `probe/probe_notify.py` は「そのチャットアプリの通知が Windows の通知センターに出るか」を最初に試す門番の小さなスクリプト。
- △ LINE for PC の通知が通知センターに載るか、本文が出るか(プレビュー設定次第)は未確認。**最初にこの probe 方式で試す**のがよい。載るなら「通知 = 起こす合図、本文は UIA で確かめる」の二段構えができ、ポーリングが要らなくなる。
- ✓ Qt の木の出し方: wechat-uia-keepalive によると、WeChat(Qt)は UIA クライアントが付いて木を辿っている間だけ完全な木を出す。LINE はすでに読めているので問題は小さいが、常駐ツールが一度切れて再接続した後に木が空になる場合の対策として、短い周期で木に触れ続ける案を覚えておく(△)。

### f. スタンプ・画像・期限切れファイル・既読

- ✓ kaosensei: 画像とスタンプは「圖片/貼圖」という文字にしかならない(本文は取れない)。
- ✓ wxauto: 画像・ファイル・音声は Name が空のボタン子要素を持ち、右クリックメニュー「コピー」などで取り出す(`_download_pic` / `_download_file`、`elements.py` 95〜150 行)。右クリックは副作用があるので、我々は「種類の判別だけ」にとどめる案。
- ✓ bensonmax は画像をキャッシュから読み、**縮小版 / 原画 / 欠落**を区別して表示する(README)。期限切れ・未取得は欠落状態として明示する設計は真似る価値がある。
- ✓ 既読: line-ext-reader は「トークを開く = 既読が付きうる」と警告。UIA で既に開いているトークを読むだけなら既読は変わらないが、**我々が別のトークを開くと相手に既読が付く**(△ 原理から。一覧のバッジ・通知で足りる所は開かない設計に)。
- ✓ 既読の数は行の Name の末尾 `既読 N` として UIA で読める(我々の観測)。自分の送信にだけ付く(△)。
- ✓ WeChat 系は撤回・拍一拍・送金などを「システム行」として分けて無視する(MsLester `ignored_system`、wxauto の `SYS/Time/Recall`)。LINE でも日付区切り・取り消し・通話の行を分類しておく。

## 3. 規約・ban リスクのまとめ

- ✓ LINE 側: 今回の調査で、LINE の利用規約が UIA 等の自動操作を明示的に禁じているかは確認できていない(△)。検索では一般の禁止事項(第 12 条)と、違反時は事前通知なくアカウント停止になりうる、という第三者の解説しか出なかった。**公式の規約本文は未確認**。
- ✓ 各 README の自己責任警告: line-ext-reader(規約違反・ban の可能性を冒頭で警告)、line-cua-mcp(実験的・規約は自己確認)、WeChatAuto.SDK(操作が多いと風控)。
- 共通して危険なのは、(1)短時間の大量操作、(2)人間離れしたタイミングでの一括送信、(3)鍵の抽出・メモリ読み出し、(4)非公式プロトコル。読むだけの UIA、人の承認つきの 1 通ずつの送信は、先行事例の中でもリスクの低い側。
- 方針案: 送信は人の承認後に 1 通ずつ、間隔を人間らしく、短時間に連続させない。1 日の送信上限と STOP ファイルを持つ(MsLester 型)。

## 4. 使えそうな順の提案(上位 5)

1. **台帳の状態機械 + 送信前の `sending` 保存 + 不明なら再送しない**(MsLester、vegeta fork)。
   送信まわりの事故(二重送信)を設計で潰せる。実装が小さく効果が大きい。
2. **宛先の窓を一意に特定し、毎回の操作の直前に前面窓を再確認**(bensonmax `AcquireExactLineTarget` / `GuardedLineSend`)。
   LINE の窓の条件 `Qt\d+QWindowIcon`・タイトル・PID・モーダル検出・大きさをそのまま使える。我々の `ChatWindow` クラス名でも同じ形で書ける。
3. **発言者判定の三点照合**(名前の前置き・`既読 N`・矩形の左右。wxauto `_split` の考え方)。食い違いは `unknown`。色判定(PrintWindow)は 4 番目の保険にする。
4. **通知の probe を最初に試す**(jev-chat-windows `probe_notify.py` + yasb の `UserNotificationListener` 実装)。
   LINE for PC の通知が通知センターに載るなら、新着はポーリングをやめて通知を合図にできる。載らなければ、一覧の未読バッジ(wxauto `GetSessionAmont`)の短周期読みに戻す。
5. **遡りはホイール + 「先頭が動かなくなったら終端」**(wxauto `LoadMoreMessage`)、**取り込みは RuntimeId で重複排除して自前の保存を正本**にする。画像は「縮小 / 原画 / 欠落」の状態を持たせる(bensonmax)。

補足: 「貼るだけで送信は人」(jev-chat-windows `fill.py`)を、確認つき返信の第 1 段階にするのがもっとも安全。送信ボタンの Invoke は、その後の段階で実機検証してから。
